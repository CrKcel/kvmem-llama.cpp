# Bonsai 固定前缀与中段召回：原因分析

2026-09-23。本文对照已有的两次 80K 运行和本地源码，没有新增长文推理实验，也没有修改推理策略。

## 新确认的事实

两次 `archive-request.json` 字节相同。GPU、模型、MTP1、K/V Q8、24K+10K 池和请求均相同；两份可执行文件的源码差异仅为缺少主机副本时打印区块编号。默认前缀 128 的结果为 1/3，512 的结果为 3/3。

| 检查项目 | 前缀128 | 前缀512 |
|---|---:|---:|
| 第一次预填充淘汰发生的批次 | [33024,33152) | [33024,33152) |
| 后续淘汰批次起点 | 41600、50176、58752、67328、75904 | 相同 |
| 读完档案时选中块数 | 192 | 192 |
| 读完档案时两者共有块数 | 176 | 176 |
| 回答召回问题时选中块数 | 192 | 192 |
| 回答召回问题时两者共有块数 | 179 | 179 |
| 召回时开头0～46号块 | 全部在场 | 全部在场 |
| 答案块1、315、568 | 全部在场 | 全部在场 |
| 各答案块及后续5块 | 全部在场 | 全部在场 |

两次在回复档案的 `OK` 之前就已选回三个答案块，并重放末尾520 token；下一轮问题又在选择后重放35 token。因此，不能把失败解释为直到生成答案时还没有取回答案，也不能解释成512版本在最终回答时才额外得到开头三个块。

问题检索阶段实际是13个块被另一组13个块替换，占192块的6.77%，相当于1664个token的位置。三个答案均不位于差异块中。默认128独有块：

```text
347 348 360 361 402 403 408 409 410 526 586 587 603
```

512独有块：

```text
57 74 88 117 131 138 226 252 263 270 535 536 537
```

分析结果：`logs/bonsai-prefix-causality-comparison.json`；生成脚本：`build-win-bonsai-release/analyze-prefix-causality.py`。

## 最值得优先检查的机制：预填充计算不同

`make_runtime_cfg` 把同一个 `sink_tokens` 设置用于预填充和最终选择。`pick_prefill_ungrouped` 在压力淘汰时先保留前缀，再以最近区块填满预算。因此改512并非只改最后一步的检索：从33K开始，每轮预填充的可见历史都发生变化。

当前适配器使用普通TopK，排序相同分数时按块编号确定次序。若评分和其他约束相同，而1～3号块本来就在TopK结果里，把它们改为必留不会导致另外13个块替换。因此，在选择器正常工作的前提下，这次差异说明检索评分的输入或其他内部状态已经不同；不能仅归因于最后强制加入三个块。评分由逐层问题Q均值与块K均值的余弦相似度聚合得到。

中段答案在约40.4K处，位于第一次淘汰之后。它的深层K/V在生成时就可能不同。K/V是模型结合上文计算的张量，不是原文的独立编码；主机和GPU字节相同只能证明搬运忠实，不能证明两次运行同一块的张量也相同。目前未保存跨运行张量或循环状态对照，不能声称已测到这种数值差异。

本地 `qwen35.cpp` 交替执行Gated DeltaNet和完整注意力，主干为64层，其中16层有注意力KV。注意力输出会进入后续循环层和更深层，因此历史可见集合的变化能够影响后续状态更新、问题Q向量以及中段块的深层K/V。循环层仍处理全部输入token；问题不在于它直接漏读了被淘汰的原文token，而在于其输入的上游隐藏表示可能已不同。

因此有一条合理但尚未完全测量的因果链：

```text
固定前缀改变
→ 33K后的注意力可见集合改变
→ 后续深层KV和循环状态可能改变
→ 问题表示、检索集合、生成logits改变
→ 中段答案的使用可能改变
```

从主机取回旧KV不会自动重新计算中间数万token。当前 `multimodal_restore` 恢复问题边界的循环检查点，随后重放问题；它恢复的是本次稀疏预填充产生的状态，不是全KV对照运行的状态。这个事实不等于恢复实现有bug。

## 其他可能共同起作用的机制

1. **其他13个块改变了注意力结果。** 即便中段块字节完全相同，输出仍取决于问题Q和所有可见K/V。注意力归一化、其他块的值以及后续层会影响中段信息是否进入答案。差异块原文主要是干扰记录，但其深层KV仍可能含有此前内容的影响，不能据原文字面判定它们毫无作用。
2. **额外保留的是有意义的内容。** 开头答案约在153～160 token，恰好落入128→512增加的范围。因此该测试把“前缀更长”和“第一个真实答案一直可见”混在一起。持续可见的罕见密码记录可能改变后续表示或任务倾向，但尚未做移位/无答案前缀对照。
3. **生成顺序放大初始差异。** 失败回答一开始就声称只有一条密码，成功回答直接列出第一条密码。后续中段答案是在不同已生成文本条件下产生的，两个漏答不能视为独立事件。缺少逐token logits，尚无法区分早期决策连锁效应和独立的中段读取失败。
4. **注意力sink是背景机制，不是已证实解释。** StreamingLLM证明保留最前面少数token可稳定窗口注意力，但本文两种策略都保留前128 token，且最终前512甚至前6016 token都在场。不能把参数名`sink`直接当成“Bonsai需要512个注意力sink”的证据。
5. **实现或数值因素尚未全部排除。** 逐层字节、位置与掩码检查降低了搬运/定位错误的可能；它不覆盖实际注意力权重、循环状态恢复的数值等价性、所有内核行为或跨运行确定性。128失败已重复出现，512成功目前只有一次。此前关闭MTP仍会失败，但本次128/512差异尚未单独做无MTP对照。

## 能区分原因的实验顺序

1. 用同一二进制重复128/512；保存首个回答token的top logits，确认差异稳定。保持采样参数显式一致。
2. 在档案结束和实际问题这两次检索都强制相同的合法192块集合（包含前四块、答案、各阶段必需尾块），改变预填充前缀策略。只固定最后一次会漏掉档案末尾520-token重放已经引入的差异。
3. 记录33K之前/之后、40K中段块和问题边界的逐层KV及循环状态摘要；先哈希定位差异，再用余弦/RMSE与logit变化判断大小。哈希不同本身不等于质量损坏。
4. 若固定集合仍有差异，再在相同token/位置边界做循环状态交换，并保留各自KV，作为诊断干预。交叉组合不是正常推理状态，结果只能用于定位，不能直接当产品修复。
5. 移走前512中的真实答案，或测试256、512、1024与多个位置/128K长文；单独询问中段密码以检查多项回答的连锁效应。单独问题也会改变检索，最好配合固定集合使用。

不建议现在直接把“循环状态清零”当作修复；这会丢掉历史信息。重放选中24K文本也只会得到删减历史的新状态，不能保证恢复完整80K计算。
