## 1. 这一版是什么

在 `v0.4.0` 的 hybrid retrieval + 独立 server 上，收 **P7-0～P7-3**（方案 B）以及 verify 时 GDN **`n_rs_seq` GPU 平面**（不再每步 150 MiB host dump）。

能用的能力：

- CLI / server 认 `--spec-type draft-mtp --spec-draft-n-max N`（与 `llama-server` 相同 flag）。Prefill 之后 decode 走 `common_speculative`，每个 target ubatch 后 `process()` 让 draft KV 跟上
- 工厂：MTP 且 `ctx_other` 是 KVMem → `llama_memory_kvmem_mtp`；池大小从 target 抄，禁止按 draft `n_ctx` 重算。`is_mem_shared` 还要求两个 context 是同一份 `llama_memory`（Gemma4），否则 Qwen 的 `ctx_other` 只给工厂找 target
- Follower：同一 `block_id` → 同一 slot、同一原始 pos。Retrieval 只打主干 K；MTP 跟 selected 集合写回。Query replay 对 draft 同一 `[p0,p1)` `seq_rm`，靠 `process()` 补后缀
- pin 之后 verify n>1 不捕主干/MTP raw-K（未 accept 的草稿不进 raw）
- Hybrid MTP reject：target `n_rs_seq = n_max`。短后缀 `seq_rm` 走 GDN GPU 平面；query replay 挖洞仍只动 attn
- 27B Unsloth `UD-Q4_K_M` 主 GGUF 已焊 `blk.64.nextn.*`，开 MTP **不必**再下 sidecar `MTP/mtp-*.gguf`

明确还没做：

- P6 Metal / Vulkan
- 128k 显存金丝雀（64k 已过关）
- DFlash2 / `--spec-type draft-dflash`
- host NeoX → `ggml_rope`；NVMe 异步 stage 的原 P3-2 退出标准

## 2. 怎么复现这一版

日常 0.8B 必须用 **MTP GGUF**（`unsloth/Qwen3.5-0.8B-GGUF` 没有 nextn）：

```bash
git checkout v0.5.0
git submodule update --init
source scripts/gpu.sh small
scripts/apply-patches.sh
scripts/build-cuda.sh
scripts/download-test-models.sh mtp   # models/unsloth/Qwen3.5-0.8B-MTP-GGUF/

python3 scripts/mtp_canary.py --gpu small
```

27B（仅 5090）：

```bash
source scripts/gpu.sh 27b
python3 scripts/mtp_vram_canary.py --gpu 27b
# needle: --no-think, --spec-type draft-mtp --spec-draft-n-max 2, budget 256
```

## 4. 速度（只记录）

27B / 5090，decode = `KVMEM_GEN_WALL`。`n_rs_seq` 之前 MTP 约 19–22 tok/s（每步 host GDN ~150 MiB）；之后 off ~40–45，**off+MTP ~50–56（约 1.2×）**。

P7-3 长 ctx（budget 256）：8k off 37.8 vs retr+MTP 61.6；64k off 32.2 vs retr+MTP 49.3。

## 5. 相对计划的落地差异

| 计划原文 | 本版本实际 |
|---|---|
| 不改 `speculative.cpp` 状态机 | 未改 draft/verify 循环。两处薄接线：MTP `ctx_other` 传给工厂；`is_mem_shared` 要求同一 `llama_memory` |

| P7-0 host `PARTIAL_ONLY` 每步 snapshot | 被 `n_rs_seq = n_max` 取代；host ckpt 仅 `draft > n_rs_seq` |
