| 项 | 值 |

成功标准是「同一条 last-user 的 tool 轮次不再把 query 之后整段后缀 replay 进 GPU budget；select 只按 recency + top-k；stream 结束有 usage」。速度不当失败。不改 FA。不窗口化 pos。不并进上游 `llama-server`。不改 OpenCode。

## 1. 这一版是什么

叠在 `v0.11.0` 的 OpenCode 长会话路径上，修两件产品行为，并补上上一版明确没进 tag 的 stream usage。

### 1.1 Same-query skip（tool 循环）

OpenCode agent 一轮里 last-user 坐标不变，后面只追加 assistant / tool。Prefix LCP 已经命中，但 `v0.11.0` 仍每轮 `apply_retrieval` + recapture query + `gdn-after-query` 把 `[query_end, n_past)` 再 decode 一遍。19 个新 token 也会 replay 2–5 万后缀。

**短路径**（`KVMEM_TRACE query_replay_skip_same` / `warm_skip=1`）在同时满足时走：

- prefix 命中（`reused=1`）
- `[query_begin, query_end)` 与上一轮相同
- `n_past > query_end`（query 已在前缀里）
- GDN / GPU seq 已在 tip
- gen-reserve 还够放下 `n_new`（`free_slots >= need_slots`）

则：**不** `apply_retrieval`、**不** recapture query、**不** `gdn-after-query`、**不** `mtp-resync` 整段后缀；只 `decode(n_past, eval_end)`。

召回窗口（budget 槽）冻结；新 tool 文本和本轮 decode 进 **gen-reserve**。

`begin_cached_turn` 仍会 unpin 以便 harvest `n_new` 的 mean-K。skip 立刻 `keep_selected`，禁止 recency pressure 把检索窗口挤掉。prefill 结束后 `pin_working_set`，后面 decode mean-K 写进 index，新 token 占 gen-reserve 而不是再跑 pressure。

新 user、prefix miss、GDN 不在 tip、或 gen-reserve 不够：退回全量 retrieval。

### 1.2 Decode/tool 后缀是 recency，不是 mandatory

`v0.11.0` 在 `apply_retrieval` 里把 **query_end 之后整段**（assistant / tool / 上一轮 decode）标成 GPU-mandatory。`recent_tokens=0` 时仍会把 2 万 tool 历史锁进 312 个 budget 槽，挤掉语义历史。

本版：

- **mandatory 只有 query span**（检索 Q）
- query 之后的 decode/tool 块走 `pick_topk` 的 **`recent_blocks`**（`--kvmem-recent-tokens / block_tokens`；**0 就是 0，不保送**）
- 其余块（含旧 tool 返回）都在 top-k 候选里：**语义相关的仍可被选中**，只是不再整段保送
- 同一条 user 的 continuation 不再 `gdn-after-query` 把后缀 decode 回 budget（否则槽位上等于又锁回去）
- skip **不再**要求「整段后缀塞得进 312」

全量 retrieval 后 312 槽 = sink + query + recency(0 则无) + top-k。当轮新 tool 文本仍走 gen-reserve / `n_new`。

### 1.3 Stream usage

`v0.11.0` 非 stream 已有 usage；OpenCode 走 stream，TUI ctx 一直为 0、auto-compact 不算 overflow。本版在 finish_reason chunk **之后**、`[DONE]` **之前**发独立 chunk：

```text
object=chat.completion.chunk  choices=[]  usage={prompt_tokens, completion_tokens, total_tokens}
```

不把 usage 粘在 finish_reason 上（OpenCode #29983 hang 类）。不发 `cached_tokens` / `reasoning_tokens`。abort 路径不发 usage。旧消息不回填。

## 2. Active KV（IQ3 例）

池：budget 312 槽（39936 tok）+ gen-reserve 125 槽（16000 tok），块 128。

同一条 user、多轮 tool：

```
Turn A  retrieval:  GPU = [sink+query+topk 312] + [本轮 decode → gen-reserve]
Turn B  skip:       GPU = [312 原样] + [A 的 decode + 新 tool + 新 decode → gen-reserve]
Turn C  skip:       同上，只往 gen-reserve 追加
…
Turn K  retrieval:  GPU = [sink+query+recency+topk 312]；旧 tool 后缀不保送，
                    分高的 tool 块可进 top-k；gen-reserve 腾空给新 decode
```

## 3. 怎么复现

```bash
git checkout v0.12.0
git submodule update --init
source scripts/gpu.sh small
scripts/apply-patches.sh
scripts/build-cuda.sh
.venv/bin/ctest --test-dir build --output-on-failure -R kvmem
python3 scripts/server_smoke.py --port 18181
```

T5 现在用 T3 的 tool_calls + tool 结果（同一 last-user），断言 `warm_skip=1` 且 `query_replay_skip_same`，且没有 `gdn-after-query` / `query_replay begin=`。新 user 的 needle 第二轮仍 `warm_skip=0` 并跑 query replay。stream 断言 usage chunk 且 `choices=[]`。

IQ3（5090）：

```bash
source scripts/gpu.sh 27b
build/bin/llama-kvmem-server \
  -m models/ISTA-DASLab/Qwen3.8-27B-GSQ-RCO-GGUF/Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp.gguf \
  --host 127.0.0.1 --port 18200 \
  -c 262144 -n 16000 -b 512 -ngl 99 \
  --kvmem --kvmem-method retrieval \
  --kvmem-budget 40000 --kvmem-gen-reserve 16000 \
  --kvmem-block-tokens 128 --kv-dtype q8_0 \
  --spec-type draft-mtp --spec-draft-n-max 2 \
  --enable-thinking --reasoning-budget 4096
```

重启后第一轮仍冷 prefill；同一 last-user 的后续 tool 轮次应出现 `warm_skip=1`。

## 5. 速度与显存（只记录）

0.8B skip 轮次 `n_new` 为几十 token，不再 replay 整段 query 后缀。IQ3 上 skip 前的 live 路径：冷 prefill ~690–900 tok/s，decode ~50–57 tok/s（MTP n_max=2，接受率 ~83%）；tool 循环里 prefill 墙钟被 query 后缀 replay 拉到 20–50s。本版目标是把那部分墙钟降到只算 `n_new`。显存仍是权重 + 有界 slot-pool，不随 256k ctx 涨。
